# Pre-registration: objective evaluation sets (RAG), 2026-11-16

Committed **before** any question in these sets is generated or run. Nothing below changes after the first run;
any deviation is reported as a deviation. The Eval team's holdout (`docs/holdout_request.md`) remains the primary
independent test; these sets add size and coverage.

## Why
The dev set (Gold v2.1, 155 questions) was used to tune `final_v1`, is 84/127 MSFT, and the extra "number + reason"
questions were few (21). We need more questions whose source, sampling and scoring do not depend on RAG.

## Who holds the sets
The Evaluation team reviews these rules (and may change any rule they judge favourable to RAG before generation),
runs `scripts/build_objective_set.py` with a seed of their choosing that RAG never sees (the manifest logs only its
hash), and keeps the question files. RAG receives only the run command, runs each set once without reading the
questions, and returns the AnswerBlocks for Eval to score. If Eval cannot hold the sets, RAG generates them with the
default seed and the report states so.

## Question source (independent of RAG)
- **Numbers**: Data's normalised metrics, `finance.metric_value`, `validation_status = passed`, `status = reported`
  (Data defines 17 metrics in `finance.metric_definition`; the builder has a template for **15** of them and draws
  only those — see the `LABEL` table in `scripts/build_objective_set.py`). Gold value = the XBRL value the company filed. Gold cell =
  the table cell Data links to that fact (`sec.cell_fact_links` → `sec.table_cells`).
- **Wording**: one fixed template per metric and period type (`scripts/build_objective_set.py`), using the metric's
  plain name, never text copied from the filing. Example: "What was Apple's total revenue for the three months
  ended June 27, 2026? Answer in USD millions." The unit asked is the table's own scale (USD thousands for a
  company that reports in thousands, e.g. Casey's; per share for EPS), so a correct answer writes the printed digits.
- **What A–C measure** (Eval 11/16, rule e): statement-table lookups with template wording on these 15 metrics. They
  are reported as such, never as the system's overall accuracy.
- **Narrative**: written by Eval or by a team member who did not tune RAG, from randomly drawn MD&A paragraphs;
  10% checked by hand. Not generated by RAG.

## Sets, sampling, sizes (seed chosen privately by the set holder)
| Set | Corpus | Population | Sample |
|---|---|---|---|
| **A — generalisation** | the 20 frozen Round 1 filings (`index_C1`, final_v1) | metric values reported in those filings | 15 per company, 150 total |
| **B — scale** | same 150 questions | asked against the full index (all passed filings in Data's DB) | 150 (paired with A) |
| **C — new companies** | full index | companies outside the Round 1 ten | 1 per company, up to 100 companies |

Two more independent sets, written by Eval and already public in kpmg-eval (Week 8/data), added 11/16 before any run:
| Set | Source | Size | Measures |
|---|---|---|---|
| **D — messy wording** | `messy_wording_v1.jsonl` (Eval): typo and casual rewrites of the dev questions, same answers | 427 | robustness to how users write (not generalisation: answers equal dev's) |
| **E — abstention** | `abstention_suite_v1.jsonl` (Eval) | 56 | declines when it should, answers when it should (twins) |
D and E are run once on `final_v1` and scored by Eval with `Week 9/scripts/grade_suite_answers.py` (answers keyed
`vid` / `sid`; questions built by `scripts/make_suite_gold.py`). Filter modes (`run_round1_reader.py --filters`):
- **D primary: no filters** (`--filters none`), amended 11/16 before any run at Eval's request (rule b): with the clean
  question's filter the 129 misspelled-company rewrites cannot fail. Co-primary: **pre-check filters**
  (`--filters precheck`, the company and period read from the messy text by `rag.coverage`; none / unresolved ->
  declined with the pre-check message, no retrieval; no company found -> whole index). Secondary: the clean
  question's Gold filters (the Agent passes the filter).
- **E: no filters** (primary) and **pre-check filters** (co-primary). Items supply no filters.
- D's primary comparison is paired against the same questions' clean dev result (McNemar), by perturbation type.
- Known before the run (counted only from question text, no answers): the rule-based extractor finds no company in
  most casual rewrites (lower-case tickers such as "msft") and does not flag unknown companies (e.g. Oracle), so in
  those items the pre-check mode equals the no-filter mode. The extractor is not changed for this run; the Agent's
  LLM extractor is the intended production path.

Stratification within each company: statement (income 6 / balance sheet 5 / cash flow 4 per 15) and period
relation (current period of the filing : prior-period comparative ≈ 2 : 1). Sampling is uniform at random
within a stratum; if a stratum is short, the remainder goes to the largest stratum of the same company.

Exclusions, applied before sampling and counted in the output:
1. value is zero or nil;
2. no table cell linked to the fact (the number is not printed in a statement table);
3. the same (company, metric, period) already drawn (comparatives repeat across filings): keep the filing whose
   reporting period equals the value's period, else the latest filing;
4. metric flagged `conflict` or `review_required`;
5. (Eval 11/16, rule a) any company × metric × period that a dev or holdout question already uses (matched on ticker,
   XBRL concept and period end of the questions' facts; `--exclude-gold`). Applied by Eval, who alone sees the holdout.

Precision (Eval 11/16, rule d): `min_sig_figs` = the significant figures printed in the linked cell, counted the way
Eval's grader counts them (trailing zeros of a whole number do not count), in the unit the question asks for.

## Systems and runs
- **Backend: every independent run (holdout A/B, sets A–E) uses Chroma** (`--backend chroma`), the backend the Agent
  serves from. Decided 11/16 before any independent run, after `scripts/backend_parity_final.py` showed Chroma and the
  custom index identical on dev at the final_v1 settings (same 3,736 chunks; identical top 5 on 127/127 questions;
  identical strict hits @10 and @15) and an end-to-end final_v1 run on Chroma reproduced NAA 0.935 / BRAA 0.977
  (154/155 reader contexts byte-identical).
- `final_v1` exactly as tagged (`configs/final_v1.yaml`), reader gpt-6.1-terra. For B/C the only change is the
  index (`index_full`, same chunking C1@460, same embedder); recorded as `final_v1@full`.
- Filters for A–C, two **co-primary** results (Eval 11/16, rule c: no user supplies the filing):
  (1) Gold filters: ticker, form and the filing's reporting period end, which pin the same single filing as dev's
  filters; (2) pre-check filters (`--filters precheck`) read from the question text.
- Each set is run once. No prompt, k or retrieval change is made on the basis of these results.

## Metrics
- **Primary**: numeric answer accuracy (NAA) with Eval's grader (`eval/vendor/kpmg_eval`), 95% Wilson interval.
- Retrieval: the gold value printed in a chunk of the gold filing within the top 15 (strict).
- Cell citation: the cell `rag.cells` cites for the answer equals Data's linked cell (same table row label and same
  column period), among questions answered correctly.
- Refusal rate on these answerable questions.

## Analyses (decided now)
1. A vs dev: NAA difference with a two-proportion interval (different question sets, unpaired).
2. A vs B: paired; McNemar exact test on the 150 questions; also retrieval@15 and wrong-period errors.
3. C: NAA and retrieval on new companies; compared with A (unpaired).
4. Breakdowns (descriptive only, no tests): statement, period relation, company.
Interpretation thresholds: a difference is called a "drop" only if the 95% interval excludes zero.

## Amendments before any run
- 11/16: Eval's review (rules a–e above): exclusion 5, precision from the printed cell and unit in the table's own
  scale, pre-check filters co-primary for A–C, D's primary run without filters, wording of what A–C measure, metric
  count corrected to 15. All made before any question was generated and before any run of D or E.

- 11/17: Chroma determinism. Re-running sets D/E showed 43 of 1,079 reader contexts differing from the first run,
  almost all in unfiltered searches. Cause: the saved HNSW graph held 3,000 of 3,736 vectors; the other 736 lived
  only in Chroma's write-ahead log and were re-inserted, multi-threaded, whenever a process opened the index, so the
  approximate dense top-100 changed between processes (~17% of unfiltered top-100 lists in a 60-query probe; top 15
  unchanged). Fix, before holdout A: the same ids and vectors (index_version 7a7ad9801f86, no re-embedding) copied
  into a collection with every vector in the saved graph (`scripts/repersist_chroma.py`); 0 of 60 lists differ
  across processes. Retrieval settings and the reader are unchanged. D/E were run on the earlier index and are
  reported as run.

## What will not be done
No tuning on A, B or C; no removal of questions after seeing answers (except the pre-stated exclusions, which are
applied before the run); no re-running with a different seed.
